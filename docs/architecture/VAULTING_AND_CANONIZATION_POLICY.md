# Vaulting and Canonization Policy

Status: Phase 1 operating doctrine
Date: 2026-04-25

## Purpose


The correct Phase 1 behavior is broad vaulting, not premature canonization.

## Core Doctrine

```text
Vault broadly.
Preserve lineage.
Do not declare canon prematurely.
Synthesize later, module by module.
```

## What “Ratified by Council” Means

A council-ratified artifact means it has been reviewed, debated, or synthesized within the user's multi-agent council workflow.

It does **not** mean:

- parent company endorsement;
- legal approval;
- production readiness;
- canonical final truth.

Council ratification is a session-level working designation unless and until separately elevated by the Convenor through a formal canonization process.

## Why Drift Is Allowed

Different agents may generate different numbering, labels, module boundaries, role titles, and architectural framings. This is acceptable during Phase 1 because the goal is to maximize useful proposal surface area.

Observed drift should be vaulted and mapped, not deleted.

Examples:

- invariant numbering collisions;
- module numbering collisions;
- Microsoft 365 Copilot vs GitHub Copilot naming ambiguity;
- council seat/title divergence;
- overlapping kernel/module proposals;
- public/private repo lineage differences.

## Phase 1: Vaulting

Phase 1 emphasizes:

- proposal capture;
- source preservation;
- module skeletons;
- registries and alias maps;
- broad architecture coverage;
- future review readiness.

Phase 1 does **not** require:

- final naming;
- final numbering;
- complete synthesis;
- production implementation;
- official vendor endorsement.

## Phase 1.5: Synthesis

Phase 1.5 begins after enough material exists to support marathon review sessions.

Phase 1.5 tasks:

- reconcile numbering;
- normalize labels;
- decide canonical module boundaries;
- merge or split duplicate proposals;
- convert forecasts into specs;
- promote selected skeletons into working code;
- identify conflicts for Convenor decision.

## Vault Entry Requirements

Every vaulted proposal should preserve:

- source agent / model;
- source workspace or repo;
- date;
- module or domain area;
- status: forecast, proposal, skeleton, ratified-working, rejected, superseded, canonical;
- sensitivity level if private repo content is involved;
- verification status for external factual claims.

## External Facts

Forecasts containing market numbers, regulations, product releases, pricing, or company claims require later verification before public or canonical use.

During vaulting, mark such claims as:

```text
provided-by-agent; pending verification
```

## Agent Instruction

When receiving a large artifact from another agent, do not flatten it into canon.

Instead:

1. vault the artifact or distilled forecast;
2. preserve provenance;
3. mark verification status;
4. map it to modules / registries;
5. defer canonization until synthesis review.

## Short Form

Nothing is canonical yet unless explicitly promoted by the Convenor after synthesis.

The system is currently in proposal accumulation + skeleton build mode.
